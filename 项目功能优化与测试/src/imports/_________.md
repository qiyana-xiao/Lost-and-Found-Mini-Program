# 校园失物招领站 — 功能说明与优化规划

> 文档目的：说明当前已实现功能、存在的不足、以及后续统一的优化方向，便于集中改造。
> 最后更新：2026-09-17

---

## 一、项目概述

校园失物招领小程序，包含失物 / 招领的发布、浏览、搜索、留言、认领等核心流程。

- 前端：微信小程序原生（TypeScript + WXML/WXSS）。
- 运行模式：**本地存储模式（不依赖微信云开发）**。数据全部保存在设备本地缓存（`wx.storage`），图片保存到本地用户目录。
- 数据层抽象：所有数据读写集中在 `miniprogram/utils/db.ts`，对外暴露 `getList / getDetail / addItem / incrementView / addMessage / closeItem / deleteItem` 七个函数，页面只依赖这套接口，不感知底层是云端还是本地。

> 设计要点：`db.ts` 的接口签名刻意与原来的云函数返回结构保持一致，因此未来若要切换回云端或接入自建后端，只需替换 `db.ts` 内部实现，页面层无需改动。

## 三、功能不足分析

### 3.1 多用户与登录（重点）

**现状**
- 本地模式下只有一个匿名 `uid`（首次启动生成，存于本地），不存在"账号"概念。
- 首页列表不按用户过滤，理论展示"所有人"的数据——但单机环境下"所有人"其实就是你自己，因此**看不到真实的其他用户发布内容**。
- 原云端版本虽天然多用户（靠微信 `OPENID` 隐式标识），但同样没有"个人中心 / 登录"这种显式账号体系。

**结论：能否做登录 + 看他人发布？**
- 可以做"登录"，但**纯本地无法看到真实他人的发布**，因为缺少跨用户共享的数据源。
- 要让"登录后见到其他人的发布"，必须引入**共享后端**（自建 HTTP 服务 + 数据库，不一定要用微信云）。此时 `db.ts` 改为调用后端接口即可，页面零改动。
- 若坚持"不依赖任何服务器"，只能做"本机多账号切换"的演示（同一设备切换不同本地身份），并非真实多用户。

**推荐方案**
1. 抽象出 `Auth` 模块（`miniprogram/utils/auth.ts`）：登录 / 登出 / 获取当前用户。
2. 登录方式二选一：
   - 微信登录（`wx.login` + 后端换取 `openid`，最契合小程序）；
   - 自建账号（手机号 / 用户名 + 密码，需后端）。
3. `db.ts` 改为请求自建后端，数据集中在服务端，`uid` 由登录态下发。
4. 个人中心（`mine`）升级为"个人主页"：头像、昵称、发布统计、我的留言、收藏等。

### 3.2 数据与持久化

- **不跨设备、易丢失**：本地缓存卸载 / 清缓存即清空，无法多人协作。→ 需后端集中存储。
- **图片配额受限**：本地 `saveFile` 有空间上限，且删除逻辑依赖路径前缀判断，脆弱。→ 后端对象存储 + CDN。
- **无离线/同步策略**：当前纯本地无冲突处理。→ 若做后端，需设计拉取/增量同步。

### 3.3 核心体验不足

| 不足 | 影响 | 优化方向 |
|---|---|---|
| 无智能匹配 | 失物招领核心价值是"配对"，现在全靠用户自己搜 | 基于标题/分类/地点/时间的相似度推荐；双向匹配提示（"有人捡到相似物品"） |
| 搜索能力弱 | 仅标题模糊匹配 | 支持地点 / 时间范围 / 排序（时间、浏览量）；分类 + 关键词联合检索 |
| "我的"页简陋 | 无统计、无资料、无设置 | 增加发布数 / 已认领数 / 浏览总量统计卡片、个人资料、设置入口 |
| 无消息通知 | 别人留言、物品被认领无感知 | 消息中心 + 微信订阅消息（需服务端） |
| 无收藏 / 关注 | 用户无法留存感兴趣条目 | 收藏夹、关注的分类或物品 |
| 无草稿 | 发布中途退出丢失内容 | 发布草稿自动保存 |
| 无举报 / 审核 | 虚假 / 恶意信息无处理 | 举报入口 + 条目状态审核流 |

### 3.4 安全与合规

- **无内容安全**：标题 / 描述 / 联系方式无敏感词过滤、无图片违规检测。→ 接入内容安全 API。
- **防刷可绕过**：清缓存即重置 `uid`，频率限制失效。→ 服务端按设备 + 账号限流。
- **联系方式暴露**：虽脱敏展示，但复制后为明文，且留言可留任意联系方式。→ 可仅对发布者开放真实联系方式的查看权限。

### 3.5 工程化

- **数据层与页面耦合**：`db.ts` 直接读写 storage，建议抽象为 `Repository` 接口，本地实现 / 远程实现可插拔。
- **无统一错误处理 / 加载态**：各页面自行 `try/catch` + Toast，风格不一。→ 封装请求层与错误提示。
- **无测试**：核心数据逻辑（筛选、分页、权限）缺少单元测试。
- **分类写死在前端**：扩展性差。→ 分类改为服务端配置 / 可运营。

## 四、优化优先级建议（路线图）

| 优先级 | 方向 | 预期收益 | 工作量 |
|---|---|---|---|
| P0 | 引入后端 + 登录体系 | 解决多用户、数据共享、看他人发布（用户核心诉求） | 高 |
| P0 | `db.ts` 接口对接后端、`auth` 模块 | 与登录配套，页面零改动 | 中 |
| P1 | 智能匹配 / 推荐 | 提升"找回"效率，产品差异化 | 中 |
| P1 | 消息通知 + 个人中心升级 | 提升留存与互动 | 中 |
| P2 | 搜索增强（地点/时间/排序） | 体验提升 | 低 |
| P2 | 收藏、草稿、举报 | 完善闭环 | 低 |
| P2 | 内容安全 / 服务端限流 | 合规与风控 | 中 |
| P3 | 工程化：Repository 抽象、统一请求层、测试 | 可维护性 | 中 |

## 五、后续统一改造的约定

为方便集中修改，建议遵循以下约定：

1. **数据访问只走 `db.ts`**：新增任何数据操作，先在 `db.ts` 暴露函数，页面不得直接读写 `wx.storage` 或发起网络请求。
2. **接口签名保持稳定**：`db.ts` 函数入参 / 出参结构尽量不变；若需扩展字段，向后兼容。
3. **登录态统一收口到 `auth.ts`**：页面取用户标识一律通过 `auth.getUid()`，不直接读 storage 里的 `uid`。
4. **开关控制运行模式**：在 `app.ts` 或 `config.ts` 增加 `USE_LOCAL` 开关，`true` 走本地存储、`false` 走后端，便于过渡期并行验证。

## 六、待确认事项（决策点）

1. 是否接受引入**自建后端**？若接受，技术栈（Node + MySQL/Postgres/MongoDB？）与部署方式需定。
2. 登录方式：微信登录（需服务端换 `openid`）还是自建账号？
3. "看他人发布"是否要求**真实多用户**，还是本机多账号演示即可？
4. 是否需要保留"纯本地、零依赖"的运行能力作为降级方案？

> 以上决策确定后，可据此推进 P0 的登录与个人中心改造。
