# 校园失物招领站 — 功能说明与优化规划

> 文档目的：说明当前已实现功能、存在的不足、以及后续统一的优化方向，便于集中改造。
> 最后更新：2026-09-30（反映本地模式 + 本机多账号演示态的真实代码状态）

---

## 一、项目概述

校园失物招领小程序，包含失物 / 招领的发布、浏览、搜索、留言、认领等核心流程。

- 前端：微信小程序原生（TypeScript + WXML/WXSS）。
- 运行模式：**本地存储模式（不依赖微信云开发，开箱即跑）**。数据全部保存在设备本地缓存（`wx.storage`），图片保存到本地用户文件目录。
- 身份体系：`miniprogram/utils/auth.ts` 提供游客 / 注册账号 / 登录 / 退出，账号数据仅存于本机缓存（**本机多账号演示，非真实跨设备多用户**）。
- 数据层抽象：所有数据读写集中在 `miniprogram/utils/db.ts`，对外暴露 `getList / getDetail / getStats / addItem / incrementView / addMessage / closeItem / deleteItem / getUnreadList / getMessageList / markItemRead / markAllRead / refreshMsgBadge` 等函数，页面只依赖这套接口，不感知底层是云端还是本地。

> 设计要点：`db.ts` 的接口签名刻意与云函数版本（`cloudfunctions/` 下的 7 个云函数）保持一致，因此未来切换回微信云开发时，只需替换 `db.ts` 内部实现，页面层无需改动。项目已预留 `cloudfunctions/` 云函数源码，见《技术架构说明》。

## 三、功能不足与局限分析（当前态）

### 3.1 多用户与数据共享（核心局限）

**现状**
- 本地模式下只有一个本机身份（`auth.ts` 管理游客 / 注册账号），数据全部在 `wx.storage`。
- 首页展示"所有人"的数据，但单机环境下"所有人"只是本机数据——**不同设备之间看不到彼此的发布与留言**。
- 账号体系是"本机多账号切换"演示，并非真实的多用户云服务。

**结论：要做真实多用户 + 跨设备共享 + 实时交互，必须切换到微信云开发（或自建后端）**
- 切换路径已就绪：`cloudfunctions/` 含 7 个云函数（与 `db.ts` 接口一一对应），前端只需把 `db.ts` 内部实现替换为 `wx.cloud.callFunction`，并初始化云环境。详见《上架微信云平台操作手册》。
- 切换后 `openid` 自动成为真实用户标识，多人发布 / 留言 / 消息即可跨设备共享。

### 3.2 数据与持久化

- **本地易丢失**：卸载 / 清缓存即清空。→ 云数据库集中存储可解。
- **图片配额受限**：本地 `saveFile` 有空间上限。→ 云存储 + CDN。
- **无离线/同步策略**：切换到云端后需考虑弱网降级（可保留本地缓存作列表缓存）。

### 3.3 核心体验不足

| 不足 | 影响 | 优化方向 |
|---|---|---|
| 无智能匹配 | 失物招领核心价值是"配对"，现全靠用户自己搜 | 基于标题/分类/地点/时间的相似度推荐；双向匹配提示 |
| 搜索能力弱 | 仅标题模糊匹配 | 支持地点 / 时间范围 / 排序；分类 + 关键词联合检索 |
| 无消息推送 | 别人留言、物品被认领无主动提醒 | 云端 + 微信订阅消息（需服务端触发） |
| 无收藏 / 关注 | 用户无法留存感兴趣条目 | 收藏夹、关注的分类或物品 |
| 无举报 / 审核 | 虚假 / 恶意信息无处理 | 举报入口 + 条目状态审核流 |

### 3.4 安全与合规

- **无内容安全**：标题 / 描述 / 联系方式无敏感词过滤、无图片违规检测。→ 接入内容安全 API。
- **防刷可绕过**：清缓存即重置账号，频率限制失效。→ 服务端按 openid 限流（云函数已含 1 分钟 3 条限制）。
- **联系方式暴露**：虽脱敏展示，复制后为明文。→ 可仅对发布者开放真实联系方式查看。

### 3.5 工程化

- **数据层与页面耦合点**：`db.ts` 直接读写 storage，已是抽象边界，切换云端时只需改此文件。
- **无统一错误处理 / 加载态**：各页面自行 `try/catch` + Toast。→ 封装请求层。
- **无测试**：核心数据逻辑缺少单元测试。
- **分类写死在前端**：扩展性差。→ 改为服务端配置。

## 四、优化优先级建议（路线图）

| 优先级 | 方向 | 预期收益 | 工作量 |
|---|---|---|---|
| P0 | 切换到微信云开发（部署云函数 + 初始化环境 + 改 `db.ts`/`upload.ts`） | 解决真实多用户、跨设备数据共享、看他人发布 | 中 |
| P0 | 实时交互（云数据库 `watch` 监听） | 新发布 / 新留言即时可见，无需手动刷新 | 中 |
| P1 | 消息推送 + 个人中心升级 | 提升留存与互动 | 中 |
| P1 | 智能匹配 / 推荐 | 提升"找回"效率，产品差异化 | 中 |
| P2 | 搜索增强（地点/时间/排序） | 体验提升 | 低 |
| P2 | 收藏、草稿、举报 | 完善闭环 | 低 |
| P2 | 内容安全 / 服务端限流 | 合规与风控 | 中 |
| P3 | 工程化：统一请求层、测试 | 可维护性 | 中 |

## 五、后续统一改造的约定

为方便集中修改，建议遵循以下约定：

1. **数据访问只走 `db.ts`**：新增任何数据操作，先在 `db.ts` 暴露函数，页面不得直接读写 `wx.storage` 或发起网络请求。
2. **接口签名保持稳定**：`db.ts` 函数入参 / 出参结构尽量不变；若需扩展字段，向后兼容。
3. **登录态统一收口到 `auth.ts`**：页面取用户标识一律通过 `auth.getUid()` / `auth.getUser()`。
4. **图片统一走 `upload.ts`**：发布图片只调用 `uploadImage`，不直接处理文件系统。
5. **运行模式切换点明确**：本地 ↔ 云端的切换集中在 `db.ts` 与 `upload.ts` 内部，以及 `app.ts` 的 `onLaunch` 初始化；不散落到页面。

## 六、待确认事项（决策点）

1. 是否正式开通微信云开发（需小程序已发布主体，个人/企业均可开通基础版）？
2. 登录方式：当前为"本机用户名+密码"演示；上云后是否改为微信 `wx.getUserProfile` / 手机号快捷登录？
3. "看他人发布"是否要求**真实多用户**（上云即可），还是本机演示已满足当前教学/演示诉求？
4. 是否保留"纯本地、零依赖"的运行能力作为降级方案（通过 `db.ts` 内部开关切换）？

> 以上决策确定后，可据此推进 P0 的云端切换与实时交互改造（见《上架微信云平台操作手册》）。
